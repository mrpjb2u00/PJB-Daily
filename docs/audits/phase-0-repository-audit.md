# Phase 0 Repository Audit

Audit date: 2026-07-22

## Project Purpose

PJB Daily is an Expo React Native productivity app by PJBStudios. The codebase is still branded as "To-Dos & Notes by PJBStudios" and centers on a calendar-driven workflow with authentication, to-dos, notes, recurrence, autosave, dark mode, profile, and daily planning surfaces.

## Technology Stack

- Expo SDK 54 / React Native 0.81.5 / React 19.1.0.
- Expo Router with file-based routes under `app/`.
- Supabase Auth and Supabase table access through `@supabase/supabase-js`.
- AsyncStorage for Supabase session persistence, theme preference, saved auth email, and editor drafts.
- React Context for auth, todos, notes, theme, and selected calendar date.
- TanStack Query client is configured globally, though the audited app data paths mainly use context state and direct Supabase calls.
- Expo modules include fonts, router, splash screen, haptics, blur, linear gradient, web browser, glass effect, symbols, and system UI.
- A Replit-oriented Express/static Expo support server exists under `server/` with static build tooling under `scripts/`.

## Repository Structure

Major directories observed:

- `app/`: Expo Router routes and modal screens.
- `app/(tabs)/`: Calendar, To-Dos, Notes, Profile, and tab layout.
- `components/`: reusable UI components, tab bar, cards, create modal, error boundary, welcome screen.
- `contexts/`: Auth, Todo, Notes, Calendar, and Theme providers.
- `constants/`: theme color tokens.
- `lib/`: Supabase client and query client.
- `utils/`: recurrence and calendar mapping utilities.
- `assets/images/`: icon, splash, adaptive icon, favicon assets.
- `docs/`: durable project docs and Phase 0 documentation.
- `server/`, `shared/`, `scripts/`: Replit/static serving and supporting build/server utilities.
- `patches/`: patch-package patch for `expo-asset`.
- `attached_assets/`: historical prompt/screenshot artifacts; not app runtime source.

No native `android/` or `ios/` directories are present. Native projects appear to be generated by Expo/EAS when needed.

## Architecture Overview

The root layout loads Inter fonts, holds the splash screen until fonts are ready, and wraps the app in providers in this order: error boundary, TanStack Query client, gesture handler root, keyboard provider, theme provider, auth provider, calendar provider, todo provider, notes provider, and root navigation.

Route protection lives in `app/_layout.tsx`. If there is no authenticated user and the current segment is `(tabs)`, web redirects to `/` through `window.location.href`; native uses `router.replace('/')`.

The root stack contains:

- `index`: welcome or authenticated redirect.
- `auth`: sign in, sign up, and forgot password.
- `(tabs)`: main authenticated app.
- `add-task`: modal task editor.
- `date-details`: calendar date details.
- `edit-note`: modal note editor.

## Major Routes And Screens

- `/`: shows loading, redirects authenticated users to `/(tabs)/calendar`, or shows welcome content.
- `/auth`: handles sign in, sign up, remembered email, and password reset.
- `/(tabs)/calendar`: planner-style month grid showing to-dos and notes by date; tapping populated dates opens date details; tapping empty dates opens create options.
- `/(tabs)/index`: To-Dos tab with filters, sorting, progress summary, active/completed grouping, edit/delete/toggle.
- `/(tabs)/notes`: Notes list with edit and delete flows.
- `/(tabs)/profile`: profile summary, counts, dark-mode toggle, account details, and sign out.
- `/add-task`: task create/edit modal with due date, recurrence, draft autosave, details, subtasks, priority, and future disabled options.
- `/edit-note`: note create/edit modal with date metadata, content editing, word count, and draft autosave.
- `/date-details`: date-centered detail view with daily progress, to-do and note sections, edit/delete/toggle actions, and add actions.

## Data And State Management

- `AuthContext` owns the current user, loading state, login, register, and logout.
- `TodoContext` owns todos, loading state, Supabase CRUD methods, recurrence type labels, and `dueDateSupported` feature detection.
- `NotesContext` owns notes, loading state, Supabase CRUD methods, and `noteDateSupported` feature detection.
- `CalendarContext` owns a single selected date string.
- `ThemeContext` owns light/dark mode and persists it in AsyncStorage.

Context state is updated optimistically only after Supabase operations return success. Errors are logged to the console and generally do not surface as persistent user-visible error states in todo/note CRUD flows.

## Authentication Flow

Supabase Auth is initialized in `lib/supabaseClient.ts` with AsyncStorage persistence, token auto-refresh, persisted sessions, and URL-session detection disabled. The app checks `supabaseConfigured` before auth operations.

`AuthProvider` loads the initial session with `supabase.auth.getSession()`, listens to `onAuthStateChange`, maps Supabase session metadata into an app user object, and exposes sign in, sign up, and sign out methods.

`app/auth.tsx` supports sign-in/sign-up toggles, validation, haptics on native, remembered last email under `@pjb_last_email`, and password reset through `supabase.auth.resetPasswordForEmail`.

Authenticated users are redirected to the Calendar tab after sign-in/sign-up success and from the root index screen.

## Supabase Usage

Supabase environment-variable names used by the app:

- `EXPO_PUBLIC_SUPABASE_URL`
- `EXPO_PUBLIC_SUPABASE_ANON_KEY`

The client falls back to placeholder values when those variables are not present and exposes `supabaseConfigured` to prevent real auth flows against placeholders.

Tables referenced in mobile app code:

- `todos`
- `notes`

Observed `todos` operations:

- feature probe: select `due_date` with limit 1.
- read: select all rows for the authenticated `user_id`, ordered by `created_at` descending.
- create: insert title, completed flag, recurrence, created timestamp, user ID, and optional due date.
- update: update title, recurrence, and optional due date by `id` and `user_id`.
- delete: delete by `id` and `user_id`.
- toggle: update completed and last completed timestamp by `id` and `user_id`.

Observed `notes` operations:

- feature probe: select `date` with limit 1.
- read: select all rows for authenticated `user_id`, ordered by `updated_at` descending.
- create: insert title, content, timestamps, user ID, and optional date.
- update: update title, content, updated timestamp, and optional date by `id` and `user_id`.
- delete: delete by `id` and `user_id`.

No SQL migrations or RLS policies were inspected remotely. No Supabase data was modified during this audit.

## Calendar And Recurrence Data Flow

The Calendar tab keeps its own viewed month/year state and reads the selected date from `CalendarContext`. It uses `getItemsMapForMonth(todos, notes, year, month)` to combine recurrence-aware to-dos and dated notes into day-cell items.

Date strings are constructed in `YYYY-MM-DD` form. Recurrence utilities parse date strings into local `Date` objects and use UTC-midnight arithmetic for day differences to avoid common timezone drift when comparing dates.

`date-details` uses `getTasksForDate(todos, date)` for recurrence-aware task lookup and filters notes by exact `note.date === date`.

## Theme And Dark Mode

Theme colors are centralized in `constants/colors.ts`. `ThemeContext` initializes from the system color scheme, then applies any stored explicit mode from AsyncStorage. The UI uses the context's `theme` object across screens and components.

The custom tab bar uses iOS light-mode blur, solid dark background in dark mode, and solid backgrounds for non-iOS/web behavior.

## Configuration Findings

`package.json` uses `expo-router/entry` as the main entry. npm is the package manager, with `package-lock.json` present.

`app.json` contains the protected identifiers under `expo`, but also contains root-level `web`, `plugins`, and `experiments` keys as siblings of `expo`. `npx --no-install expo config --type public` confirmed Expo warns:

`Root-level "expo" object found. Ignoring extra keys in Expo config: "web", "plugins", "experiments"`

The exact file causing this is `app.json`. The current structure means these settings are ignored by Expo:

- `web.favicon`
- `plugins`: `expo-router` with origin, `expo-font`, `expo-web-browser`
- `experiments.typedRoutes`
- `experiments.reactCompiler`

Likely practical impact:

- The favicon path may not be applied through Expo config.
- The explicit plugin list may not be applied from `app.json`; some plugins may still be auto-applied by installed packages or defaults, but this should not be relied on.
- Typed routes and React Compiler experiment flags may not be active through Expo config.

Safe future correction: move `web`, `plugins`, and `experiments` inside the `expo` object in a dedicated config-only change, then re-run `expo config`, lint, TypeScript, and a dev-server start check. Do not alter protected production identifiers while doing this.

`eas.json` uses EAS CLI version `>= 18.0.6`, `appVersionSource: "remote"`, and production `autoIncrement: true`.

Android `versionCode` and iOS `buildNumber` are not set in `app.json`. With `appVersionSource: "remote"`, build numbers appear to be managed by EAS remote versioning, with production auto-increment enabled.

No `app.config.js` or `app.config.ts` is present.

## Commands Run And Outcomes

- `npx --no-install expo config --type public`: passed with warning. It loaded `.env` and exported only public environment variable names in output; no values were displayed here. Warning confirmed root-level ignored config keys in `app.json`.
- `npm run lint`: failed with 1 lint error and 8 warnings. Error is `react/no-unescaped-entities` in `app/auth.tsx`. Warnings include unused variables/imports, duplicate imports, and missing hook dependencies.
- `npx --no-install tsc --noEmit`: failed. Errors include NativeTabs icon prop/type mismatches, invalid `headerStatusBarHeight` option typing, and an implicit `any` in `server/index.ts`.
- `npx --no-install expo-doctor`: could not run because `expo-doctor` is not installed and `--no-install` prevented installing it.
- Expo dev server start check: Metro started and `/status` responded successfully. The server was stopped after verification. The same root-level Expo config warning appeared on startup.

## Development Server Result

The Expo development server started successfully enough for Metro to respond on `http://localhost:8081/status`. No device or emulator testing was performed, so this audit does not verify actual runtime behavior on hardware.
